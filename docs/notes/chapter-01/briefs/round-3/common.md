# Instructions for every Chapter 1 brief in the third round

You are redrafting learner-facing text for an interactive course, *Metadata Systems*, after the
author's third round of feedback. Read these first, in full:

- `docs/notes/chapter-01/facts.md`: the only facts you may use. Every number, name and time you
  write must be in it. Do not invent a number, a name, a time or a behaviour.
- `docs/style.md`: the style checklist. Apply both passes.
- `docs/notes/chapter-01/briefs/round-2/common.md`, and the files it names: every rule there still
  holds.

What this round changes, so that your text serves it:

- **Question the requirement.** The course teaches a habit, not only facts: when a requirement
  sounds obvious, ask what question it is actually asking, and why that answer is needed. A
  requirement can be read in several reasonable ways; the text never calls one reasonable reading
  wrong, and "there is not enough to choose yet" can be the right place to stop.
- **"Owner" has several meanings on this page, on purpose.** Never use the word alone where it
  could mean more than one. Say "the warehouse's owner" for the account the warehouse records;
  write the requirement's word as "owner", in quotation marks, when you mean the word itself.
- **Responsible** is the one word for who answers for an asset. "Answer" is for questions only.
  A program is never a "job". Do not use the word "metadata": this text comes before the chapter
  introduces it.

Each key below says where the text appears and lists the facts it must carry. The facts are a
list, not wording: write your own sentences. Keep every `{slot}` exactly as written, braces
included, and add no other slot. Where a key says plain text, write no Markdown and no backticks.
Where a key says names in backticks, put each name of an asset, an account or a slot that holds
one between backticks, as in `daily_sales`.

Write your draft to the file your brief names, as Markdown with one `## key` heading per item, in
the brief's order, and nothing else under each heading but the text itself. For a key that takes
several labels, write them as a Markdown list with the label's key before a colon
(`person: ...`), in the brief's order.
