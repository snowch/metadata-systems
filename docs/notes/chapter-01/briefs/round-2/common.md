# Instructions for every Chapter 1 brief in the second round

You are redrafting learner-facing text for an interactive course, *Metadata Systems*, after the
author's second round of feedback. Read these first, in full:

- `docs/notes/chapter-01/facts.md`: the only facts you may use. Every number, name and time you
  write must be in it. Do not invent a number, a name, a time or a behaviour.
- `docs/style.md`: the style checklist. Apply both passes.
- `docs/notes/chapter-01/briefs/common.md` and `docs/notes/chapter-01/briefs/revision/common.md`:
  the rules every Chapter 1 brief follows. They all still hold.

What this round changes, so that your text serves it:

- **A prediction asks for a belief the learner can already hold.** Each option of a prediction is
  an explanation of how the platform works, not a number or a fact to guess. Write each option as
  its explanation, in a few words. The options of one prediction are parallel: the same form and
  about the same length, so that no option looks right because of its wording. A question shown
  before the learner commits must not say or hint which explanation the lab will support.
- **"Map" means the map of the platform, and nothing else.** The figure that sorts the questions is
  never a map.
- **"Asset" is defined once, early, and used the same way after.** "Metadata" is defined once, in
  the generalisation, and never as information kept apart from the data.
- **The learner does before they are told.** Where a brief says a text asks a question, it asks it
  and does not answer it.

Each key below says where the text appears and lists the facts it must carry. The facts are a
list, not wording: write your own sentences. Where a key gives the text it replaces, keep what the
facts do not change, and change only what they do. Keep every `{slot}` exactly as written, braces
included, and add no other slot. Captions, option labels, button labels and headings are plain
text: no Markdown, no backticks, and no full stop unless the key says so.

Write your draft to the file your brief names, as Markdown with one `## key` heading per item, in
the brief's order, and nothing else under each heading but the text itself. For a key that takes
several labels, write them as a Markdown list with the label's key before a colon
(`yes: ...`), in the brief's order.
