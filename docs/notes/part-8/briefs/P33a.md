## B

- The heading `### The ferry's platform`.
- You have joined the data team of an island ferry. It crosses between the mainland and the island
  three times a day from each side: from the mainland at 07:30, 12:30 and 17:30, and from the island
  at 09:30, 14:30 and 19:30.
- Each harbour has two ticket gates. A minute after each departure, each gate uploads the sailing's
  scans to object storage as one batch, in the bucket `ferry-gates`: one scan per line, with the
  ticket, the fare and the time it was scanned, `scanned_at`.
- A change to a batch starts a function. `load_scans` starts when a batch is created or overwritten,
  and puts its scans into the warehouse table `boardings`. `drop_scans` starts when a batch is
  deleted, and removes its scans from `boardings`.
- At 01:00 each night, the job `build_loads` counts the day before's passengers for each sailing
  into the table `sailing_loads`. At 06:00, the job `send_report` writes those counts to a file in
  the bucket `ferry-reports`, and the harbour masters get the file by email.
- On Friday 25 at 09:00, the operations manager sends three messages. Write them as a list, each in
  double quotation marks:
  - "Thursday afternoon's sailings from the island look nearly empty. The harbour master counted far
    more people on board."
  - "Tuesday's 17:30 from the mainland shows 35 passengers. `boardings` has 38."
  - "An engineer's test batch got into Wednesday's figures. It was deleted on Thursday morning."

## F

- "Record the lineage of every boarding" could mean three things. Each item says what it needs (a
  list):
  - per scan: each row of `boardings` needs the batch it came from. `boardings` keeps the batch's
    name, in its column `batch`, and not its version;
  - per batch: each run of a function needs to name the batch it read;
  - per version: each run needs to name the batch and the version it read, so that a figure can be
    traced to the versions it counted. The first question needs this one.
- The requirement does not say which it means. This page builds to the third. With the column
  `batch`, it answers the first two as well.
- Each batch is one dataset, named by its key in `ferry-gates`. The version a run read goes on that
  run's input, in OpenLineage's `version` facet, whose field is `datasetVersion`, as the shop's
  returns desk did in Chapters 7 and 8. A batch's versions stay one dataset over time.
- The other choice, a dataset for each version, gives each version its own node in the graph; a
  reader then needs the key to find a batch's versions. Neither choice is wrong.
- The heading `### Instrumenting the functions`.
- The ferry's function platform builds each function run's OpenLineage events. The inputs come
  from a piece of code you write, `inputs(change)`.
- `change` holds the batch's bucket and key, what happened (`"created"`, `"overwritten"` or
  `"deleted"`), the new version, and the version before it, `previous`, where there was one.
- As it stands, `inputs` names the batch without its version for a create or an overwrite, and
  nothing for a delete. The shop's `remove_return`, in Chapters 7 and 8, named no input either.
- A run of `drop_scans` reads nothing: the batch is gone. Naming the version it removed as its
  input is the ferry's choice: it links the removal to the batch.
- Change `inputs` so that each run names the version it read, and a delete names the version it
  removed. `shop.ferry.version_facet(version)` makes the `version` facet. Select the cell and press
  **Run below**.
- The check below it tests every function run of the three days. As `inputs` stands, 1 of 3 tests
  passes. The cell after the check prints the event of the run that the delete of the test batch
  started.

## G

- With the change, all 3 tests pass. The delete's event names the test batch with the version
  `e622b165c27a`, the version the engineer deleted.
- OpenLineage has a facet for a change to a dataset, `lifecycleStateChange`, with values such as
  `CREATE`, `OVERWRITE` and `DROP`. It describes a change a run makes to a dataset. The gates and
  the engineer changed the batches, not the functions, so the ferry records the change that started
  a function in a facet of its own, `ferry_batchChange`.
