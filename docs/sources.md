claim about a standard or a product that this file does not support is not stated as fact
(`CLAUDE.md`, "Accuracy"). Quotations here are short, marked, and attributed; nothing from these

## OpenLineage

The OpenLineage project's code and specification are under the Apache License, Version 2.0
(`LICENSE` in `OpenLineage/OpenLineage`). The course uses the specification's interface names
(event types, field names, facet names) as names, describes the rest in its own words, and does
not copy the schema files.

### The specification, as JSON Schema

`spec/OpenLineage.json` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026. Its `$id`
is `https://openlineage.io/spec/2-0-2/OpenLineage.json`. It supports these claims:

- There are three kinds of event: a run event, a dataset event and a job event. A run event
  requires `eventTime`, `producer`, `schemaURL`, `run` and `job`; a dataset event has a `dataset`
  and no `job` or `run`; a job event has a `job` and no `run`.
- A run event's `eventType` is one of `START`, `RUNNING`, `COMPLETE`, `ABORT`, `FAIL` and
  `OTHER`. The field's description says: "It is required to issue 1 START event and 1 of [
  COMPLETE, ABORT, FAIL ] event per run."
- A run is identified by `runId`, in UUID format. A job and a dataset are each identified by a
  `namespace` and a `name`. Input and output datasets extend a dataset with input-specific and
  output-specific facets.
- Every facet carries `_producer` and `_schemaURL`, both URIs; facets allow fields beyond those.
- `eventTime` is a date-time; `producer` and `schemaURL` are URIs.

### The specification document

`spec/OpenLineage.md` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026:

- the core model: a job is "a process definition that consumes and produces datasets"; a run is
  "an instance of a running job with a start and completion (or failure) time"; a dataset is "an
  abstract representation of data";
- "All metadata is additive": a producer may send further events about a run without repeating
  what it sent before;
- "A run ID **must** be a UUID";
- a facet is "an atomic piece of metadata identified by its name", versioned by its `_schemaURL`;
  custom facets are allowed with a prefix;
- the parent run facet records the job and run that spawned a run.

### The documentation pages

From `website/docs/spec/` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026:

- `run-cycle.md`: the six run states and what each signals; `COMPLETE`, `ABORT` and `FAIL` are
  terminal, and "Sending any of terminal events means no other events related to this run will be
  emitted"; `OTHER` may be sent at any time before a terminal state, even before `START`; "Unless
  specified otherwise, we assume events describing a single run are **accumulative**". The page
  also distinguishes jobs by the job type facet's `processingType`. A BATCH job emits `START`, an
  optional `RUNNING`, then `COMPLETE`, `FAIL` or `ABORT`, and its events are typically
  accumulative. STREAMING and SERVICE jobs have "No expected terminal event under normal
  operation" and typically emit periodic events, each a complete snapshot of a time window; the
  page names an `eventCompleteness` field that says which kind an event is. Neither this page,
  `object-model.md` nor `spec/OpenLineage.md` says what a consumer does with a missing, duplicated
  or late event (a text search of all three for duplicates, ordering, lateness, retries and
  delivery guarantees, 6 October 2026, found nothing).
- `object-model.md`: a job is "a process that consumes or produces Datasets", identified by a
  unique name within a namespace; a run is "an instance of a Job that represents one of its
  occurrences in time", with a `runId` "generated by the client" as a UUID, UUIDv7 recommended; a
  dataset has a unique name within a namespace derived from its physical location; "a lineage
  graph can be created by weaving together observations of many Jobs across multiple platforms".
  The page separates runtime lineage, a run event "emitted at runtime", from design lineage: a job
  event describes a job's static properties "such as its location in source code or declared
  inputs/outputs", and a dataset event describes metadata changes to a dataset, both "Emitted at
  design-time and not associated with a `Run`". Chapter 5's declared and observed dependencies
  rest on this distinction.
- `naming.md`: a dataset's namespace names the data store and its name names the dataset inside
  it. PostgreSQL: `postgres://{host}:{port}` and `{database}.{schema}.{table}`. S3:
  `s3://{bucket name}` and the object key. BigQuery: `bigquery` and `{project id}.{dataset
  name}.{table name}`. Kafka: `kafka://{bootstrap server host}:{port}` and the topic. Local file
  system: `file` and the path. "The job namespace is usually set in OpenLineage client config. The
  job name is unique within its namespace."

### The standard facets

The schema files in `spec/facets/` of `OpenLineage/OpenLineage`, branch `main`, listed 6 October
2026, name the standard facets, among them: `SchemaDatasetFacet`, `ColumnLineageDatasetFacet`,
`DataQualityMetricsInputDatasetFacet`, `DataQualityAssertionsDatasetFacet`,
`OutputStatisticsOutputDatasetFacet`, `OwnershipDatasetFacet`, `SymlinksDatasetFacet`,
`DatasetVersionDatasetFacet`, `LifecycleStateChangeDatasetFacet`, `ParentRunFacet`,
`NominalTimeRunFacet`, `ErrorMessageRunFacet`, `SQLJobFacet`, `SourceCodeLocationJobFacet` and
`JobTypeJobFacet`. A chapter that describes a facet's fields reads that facet's schema file first
and records it here.
