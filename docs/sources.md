claim about a standard or a product that this file does not support is not stated as fact
(`CLAUDE.md`, "Accuracy"). Quotations here are short, marked, and attributed; nothing from these

## OpenLineage

The OpenLineage project's code and specification are under the Apache License, Version 2.0
(`LICENSE` in `OpenLineage/OpenLineage`). The course uses the specification's interface names
(event types, field names, facet names) as names, describes the rest in its own words, and does
not copy the schema files.

### The specification, as JSON Schema

`spec/OpenLineage.json` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026. Its `$id`
is `https://openlineage.io/spec/2-0-2/OpenLineage.json`. It supports these claims:

- There are three kinds of event: a run event, a dataset event and a job event. A run event
  requires `eventTime`, `producer`, `schemaURL`, `run` and `job`; a dataset event has a `dataset`
  and no `job` or `run`; a job event has a `job` and no `run`.
- A run event's `eventType` is one of `START`, `RUNNING`, `COMPLETE`, `ABORT`, `FAIL` and
  `OTHER`. The field's description says: "It is required to issue 1 START event and 1 of [
  COMPLETE, ABORT, FAIL ] event per run." It goes on to allow further `OTHER` events in the same
  run, "For example to send additional metadata after the run is complete". The run-cycle page
  (below) disagrees: there, a terminal event means nothing more about the run will be sent, and
  `OTHER` comes before a terminal state. The course states both and says that they differ.
- A run is identified by `runId`, in UUID format. A job and a dataset are each identified by a
  `namespace` and a `name`. Input and output datasets extend a dataset with input-specific and
  output-specific facets.
- Every facet carries `_producer` and `_schemaURL`, both URIs; facets allow fields beyond those.
- `eventTime` is a date-time; `producer` and `schemaURL` are URIs.

### The specification document

`spec/OpenLineage.md` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026:

- the core model: a job is "a process definition that consumes and produces datasets"; a run is
  "an instance of a running job with a start and completion (or failure) time"; a dataset is "an
  abstract representation of data";
- "All metadata is additive": a producer may send further events about a run without repeating
  what it sent before;
- "A run ID **must** be a UUID";
- a facet is "an atomic piece of metadata identified by its name", versioned by its `_schemaURL`;
  custom facets are allowed with a prefix;
- the parent run facet records the job and run that spawned a run.

### The documentation pages

From `website/docs/spec/` in `OpenLineage/OpenLineage`, branch `main`, read 6 October 2026:

- `run-cycle.md`: the six run states and what each signals; `COMPLETE`, `ABORT` and `FAIL` are
  terminal, and "Sending any of terminal events means no other events related to this run will be
  emitted"; `OTHER` may be sent at any time before a terminal state, even before `START`; "Unless
  specified otherwise, we assume events describing a single run are **accumulative**". The page
  also distinguishes jobs by the job type facet's `processingType`. A BATCH job emits `START`, an
  optional `RUNNING`, then `COMPLETE`, `FAIL` or `ABORT`, and its events are typically
  accumulative. STREAMING and SERVICE jobs have "No expected terminal event under normal
  operation" and typically emit periodic events, each a complete snapshot of a time window; the
  page names an `eventCompleteness` field that says which kind an event is. Neither this page,
  `object-model.md` nor `spec/OpenLineage.md` says what a consumer does with a missing, duplicated
  or late event (a text search of all three for duplicates, ordering, lateness, retries and
  delivery guarantees, 6 October 2026, found nothing).
- `object-model.md`: a job is "a process that consumes or produces Datasets", identified by a
  unique name within a namespace; a run is "an instance of a Job that represents one of its
  occurrences in time", with a `runId` "generated by the client" as a UUID, UUIDv7 recommended; a
  dataset has a unique name within a namespace derived from its physical location; "a lineage
  graph can be created by weaving together observations of many Jobs across multiple platforms".
  The page separates runtime lineage, a run event "emitted at runtime", from design lineage: a job
  event describes a job's static properties "such as its location in source code or declared
  inputs/outputs", and a dataset event describes metadata changes to a dataset, both "Emitted at
  design-time and not associated with a `Run`". Chapter 6's declared and observed dependencies
  rest on this distinction.
- `naming.md`: a dataset's namespace names the data store and its name names the dataset inside
  it. PostgreSQL: `postgres://{host}:{port}` and `{database}.{schema}.{table}`. S3:
  `s3://{bucket name}` and the object key. BigQuery: `bigquery` and `{project id}.{dataset
  name}.{table name}`. Kafka: `kafka://{bootstrap server host}:{port}` and the topic. Local file
  system: `file` and the path. "The job namespace is usually set in OpenLineage client config. The
  job name is unique within its namespace."

## W3C PROV (Chapter 15)

*PROV-DM: The PROV Data Model*, W3C Recommendation, 30 April 2013
(https://www.w3.org/TR/prov-dm/), read 12 October 2026, for checking and not copied. It supports:
provenance in PROV is information about the entities, activities and people involved in producing a
piece of data or a thing; an entity is a thing "with some fixed aspects", so that a thing in two
states is two entities (its own example is a car in two cities); an activity occurs over a period of
time and uses or generates entities; an agent bears responsibility for an activity or an entity; its
relations include usage (an activity using an entity), generation (an entity generated by an
activity) and derivation (one entity derived from another). The document notes that the provenance
of something that changes, such as the data behind a daily report, is hard to express precisely.
W3C documents are published under the W3C document licence; nothing from it is copied.

## Apache Iceberg's schema evolution (Chapter 11)

`format/spec.md` in `apache/iceberg`, branch `main`, read 12 October 2026. It supports: a schema can
evolve by adding, deleting, renaming and reordering fields; "Adding a new field assigns a new ID for
that field"; "Renaming an existing field must change the name, but not the field ID"; and columns in
data files are selected by field id, not by name. Chapter 11 states that a column's id survives a
rename, so Iceberg's schemas can tell a rename from a removal and an addition. The specification is
under the Apache License, Version 2.0; nothing from it is copied.

## A table's owner in PostgreSQL (Chapter 2's closing note)

PostgreSQL's documentation, the section "Privileges" (`doc/src/sgml/ddl.sgml` in
`postgres/postgres` at the branch `REL_18_STABLE`, commit `1370a78`), read 7 October 2026 from
the repository, because postgresql.org refused the build environment. When an object is created
it is given an owner, "normally the role that executed the creation statement"; for most kinds of
object only the owner (or a superuser) can do anything with it at first, and other roles use it
once privileges are granted; the right to modify or destroy an object comes with being its owner
and cannot be granted on its own. A role here is what the course calls an account.

It supports the closing note's sentences on PostgreSQL, and the fourth reading of Chapter 2's
requirement, "which account controls `daily_sales` in the warehouse?": a warehouse's owner is an
account with rights over the table, an answer to a question about control, not about who is
responsible. The note says "some real databases": not every database gives a table an owner, and
the course claims nothing about the others.

## An owner for every dataset as practice (Chapter 2's requirement; Chapter 8)

Read 12 October 2026, for checking and not copied. No standard states "every table must have an
owner"; the course says only that data teams often adopt the rule, and these show the practice
built into tools that are widely used:

- dbt's documentation, "Add groups to your DAG" (`website/docs/docs/build/groups.md` in
  `dbt-labs/docs.getdbt.com`, branch `current`): every group has an owner, and `owner` is required;
  it identifies who is responsible for the group, by a name or an email.
- OpenLineage's `spec/facets/1-0-0/OwnershipDatasetFacet.json`, from openlineage.io: a dataset facet
  whose `owners` each have a required `name` and an optional `type`. The schema recommends a URN for
  the name and gives as examples an application, a user and a team (`application:foo`, `user:jdoe`,
  `team:data`); its example `type` is `MAINTAINER`. So the standard records an owner and leaves open
  whether it is a person, a team or a program, the readings Chapter 2 sets apart. Chapter 8 says so;
  the shop does not send this facet.

A search for the rule in data-mesh writing found practitioner articles that put a named owner per
dataset first, and none that is a standard; they are not cited on the page.

## A description inside the database (Chapter 3's closing note)

PostgreSQL's reference page for `COMMENT` (`doc/src/sgml/ref/comment.sgml` in `postgres/postgres`
at the branch `master`, commit `a241bc4`), read 12 October 2026 from the repository, because
postgresql.org refused the build environment. `COMMENT` stores, replaces or removes the comment on
a database object, a column included (`relation_name.column_name`); only one comment string is
stored for each object, and a new one replaces it; for most kinds of object only the owner (or a
superuser) can set it; `psql`'s `\d` family of commands shows comments, built on the functions
`obj_description` and `col_description`.

It supports the closing note of Chapter 3: some real databases keep a description with a table or
a column, inside the database. The note says "some": the course claims nothing about databases it
has not read.

## The web app manifest and home-screen icons (the course's icon)

Read 7 October 2026, for the course's icon and its manifest (`scripts/icons.mjs`,
`apps/course/public`). w3.org, web.dev and developer.chrome.com were not reachable from the build
environment, so each is read from its source or its publisher's own copy:

- **Web Application Manifest**, the W3C Editor's Draft, from its source in `w3c/manifest` at the
  commit `8ae3046`. `start_url` and `scope` are resolved against the manifest's own address, and
  without a `scope` the scope is the start URL's directory. An `id` is resolved against the start
  URL's origin, not its path, and without one the id is the start URL: so on an origin the
  author's courses share, the course leaves `id` out. An icon's `purpose` is `any` (the default),
  `maskable` or `monochrome`. A maskable icon's safe zone, the part always visible whatever mask a
  platform applies, is a circle about the icon's centre with a radius of two fifths of its size.
  `theme_color` is the application's default theme colour, which a page's `theme-color` tag may
  override; `background_color` is drawn while the application loads, before its stylesheet is
  there. `color_scheme_dark` gives either colour for a system in dark mode; it is new in the draft,
  and a browser may not yet honour it. `standalone` display opens the application without the
  browser's own controls, such as the address bar.
- **Apple, Safari Web Content Guide, "Configuring Web Applications"** (developer.apple.com,
  archived documentation). A `link` with `rel="apple-touch-icon"` names the icon iOS puts on the
  home screen; with none, iOS looks for `apple-touch-icon.png` at the site's root, which on
  `snowch.github.io` is not this course's. The sizes it lists run up to 180 pixels, and a device
  without an icon of the size it wants takes the smallest larger one.
- **Apple, Human Interface Guidelines, "App icons"** (developer.apple.com, read as the page's
  data). On iOS an icon is square and the system masks it to rounded corners; the main content is
  kept centred, so the mask does not cut it. This is why the course's iOS icon is filled to its
  edges.
- **MDN, "Making PWAs installable"**, from `mdn/content` at the commit `306f0d1`. Chromium-based
  browsers offer to install a site whose manifest has a `name` or `short_name`, icons of 192 and
  512 pixels, a `start_url`, a `display` (or `display_override`), and no
  `prefer_related_applications` set to true, served over HTTPS; a service worker is not required.

## SQLite's query plan (Chapter 24)

Read on 13 October 2026, in SQLite's source: `src/wherecode.c` in the project's GitHub mirror
(`sqlite/sqlite`, branch `master`, commit `264c92b92307999ffc5c256bd11f5193b4f629de`, version
3.55.0), the function that writes one line of `EXPLAIN QUERY PLAN` for each loop over a table.

- A loop that reads every row of a table is written `SCAN` and the table's name; one that looks rows
  up by a constraint is written `SEARCH` and the table's name.
- A search through an index adds `USING INDEX` and the index's name (`USING COVERING INDEX` when the
  index holds every column the query needs), then, in brackets, the index's columns the search
  constrains, as `column=?` joined by `AND` (`explainIndexRange`).
- These are the words the shop's store reads to count the rows a query reads (`shop/store.py`,
  `Tables.rows_read`). `notebook/tests/test_engine.py` pins the two plans the chapter shows, in the
  SQLite the tests run (3.45.1 on 13 October 2026), and the notebooks' browser test checks the
  counts in the SQLite the page runs.
- Not read: SQLite's page on `EXPLAIN QUERY PLAN` (`sqlite.org/eqp.html`), which the proxy refused.
  The course says nothing about whether the plan's wording stays the same between versions.

### OpenLineage (`OpenLineage/OpenLineage`, `main`, commit `60261f0b57fb1370c2c6c3cadc9f1721b6c3c3b5`)

- `README.md`: Marquez "is the reference implementation of the OpenLineage API" (quoted).
- `spec/facets/`: there is no facet for a trained model's training or evaluation; a dataset's type
  may be given as `MODEL` among others (`DatasetTypeDatasetFacet`, 1-0-1), a dataset's version as
  text (`DatasetVersionDatasetFacet`, 1-0-1), and its owners as a list of a `name` and an optional
  `type` (`OwnershipDatasetFacet`, 1-0-1).
- The Spark integration (`integration/spark/shared/.../api/naming/JobNameBuilder.java`,
  `NameNormalizer.java`): the job name is the application's name, the executed plan's top node put
  through the normaliser, and a suffix from the output, with `.` made `_`; the normaliser splits
  words at changes of case, lower-cases them and joins them with `_`. For an insert into a table kept
  as files, the suffix is the last two parts of the output's path joined with `_`
  (`InsertIntoHadoopFsRelationVisitor.jobNameSuffix`, `JobNameSuffixProvider.trimPath`); the
  project's own test event `pysparkHadoopFSEndEvent.json` has the output `/tmp/warehouse/test` and a
  job ending `execute_insert_into_hadoop_fs_relation_command.warehouse_target`. Where the shop's
  table's files are kept is the shop's assumption.
- The dbt integration (`integration/dbt/src/openlineage/dbt/__init__.py`;
  `integration/common/src/openlineage/common/provider/dbt/processor.py`, `local.py`): `dbt-ol` runs
  dbt as a child process and, at the end, reads `manifest.json` and `run_results.json` and sends the
  events; the job namespace is `OPENLINEAGE_NAMESPACE`, else `dbt`; a model's job is its database,
  schema and unique id without `model.`, joined with `.`; each model's run id is a new UUID made when
  the artifacts are read.

### Marquez (`MarquezProject/marquez`, `main`, commit `180f37b22387146187af1ef0279e3ee1d1ccd789`)

- `api/.../db/OpenLineageDao.java`: every run event is inserted into `lineage_events`; a state is
  taken from the event's type (`complete` to `COMPLETED`, `abort` to `ABORTED`, `fail` to `FAILED`,
  `start` and any other type to `RUNNING`), and for an event with a type a state row is written and

- `api/.../service/models/`: only `Namespace` and `NamespaceMeta` have an owner; datasets, jobs, runs
  and sources have none. `api/.../search/SearchConfig.java`: search is off by default

  PostgreSQL; `docs/docs/quickstart/index.mdx`: its model is namespaces, sources, datasets, jobs and

### Airflow's OpenLineage provider (`apache/airflow`, `main`, commit `7f0d50cffc61a48650590078f6832b349860322b`, provider 2.20.3)

- `extractors/manager.py`, `extract_metadata`: a task's inputs and outputs come from the extractor

  `inlets` and `outlets`. A task that reports nothing by any of these sends no datasets.
- `plugins/adapter.py`, `_build_job`: a task's job facets are those its extractor returns, with
  `documentation`, `ownership` and `tags` when the task has them, and `jobType`; a task's run facets
  include `parent` (with a `root`), `airflow` and `processing_engine` (research note for Chapter
  29, section 4); the Dag's own run sends events as a job named for the Dag.

  reading, only the tag `providers-openlineage/2.20.3rc1` exists.

- Airflow itself (`apache/airflow`, tag 3.3.0): the task instance table calls itself the "single
